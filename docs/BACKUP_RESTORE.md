Inventory existing application/Auth/Storage rows and require zero user/academic objects. 2. Keep the app, SMTP/webhooks, cron, AI/TURN and public signup disconnected on the target. Database restore can copy operational job definitions or secrets; review/exclude those deliberately. Use an isolated CLI work directory instead of relinking the source checkout. Configure required supported extensions and compare platform versions before restoration. Maintain `tests/staging-preflight.sql` compatibility; never restore a whole managed platform schema over its fresh provider version without the documented migration process.
3. Privately inspect roles/schema/data/history/customization files. Resolve expected provider-managed role/schema conflicts in a target-specific reviewed restore packet **before execution**. The provider's documented logical procedure uses `session_replication_role=replica` while loading data; require administrator support, then restore normal mode and validate all constraints/triggers afterward. Review whether the history schema already exists on the empty target before restoring it. Never modify source dump bytes silently; retain original hashes and a reviewed patch.
